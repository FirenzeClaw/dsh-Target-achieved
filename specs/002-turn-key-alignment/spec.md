# Feature Specification: 轮次键对齐（声明与判定共用同一轮次坐标）

**Feature Branch**: `002-turn-key-alignment`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "实测发现：一轮里第一次调用 target_status 时，工具把声明写到上一轮的键上（首轮为 0），收尾判定按当前轮取到的是全新的未声明状态，于是仍然注入。只有被注入之后的第二次声明才生效。要求走 spec 流程固定这个缺陷，并补回回归测试。"

## 背景与缺陷证据

2026-11-05 真实会话实测（宿主 0.2.1-rc.5，插件已挂载）：

| 轮次 | 动作 | 工具返回 | 收尾判定 |
|---|---|---|---|
| 3 | 轮次开头声明 `awaiting_user` | `turn: 0` | 判为未声明 → 注入（attempt 1） |
| 3 | 注入后再次声明 `done` | `turn: 3` | 判为已声明 → 放行 |
| 4 | 轮次开头声明 `awaiting_user` | `turn: 3` | 判为未声明 → 注入（attempt 1） |
| 4 | 注入后再次声明 `awaiting_user` | `turn: 4` | 判为已声明 → 放行 |

结论：一次正常、自觉的声明**永远不会被看见**；插件只有在已经把助手拽回来一次之后，才开始尊重它的声明。对用户而言表现为每轮都被无谓地催促一次。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 助手主动声明后不再被催促 (Priority: P1)

助手在完成任务后主动声明目标状态，然后收尾。用户看到的是干净的一轮结束，而不是被插件多推一步。

**Why this priority**: 这是插件能否被正常使用的前提。若主动声明不被承认，插件就从"防中断"退化成"每轮必催一次"的噪音源，用户会直接关掉它。

**Independent Test**: 构造一个"轮次一开始就声明完成、随后收尾"的轮次，确认不产生任何自动提醒。

**Acceptance Scenarios**:

1. **Given** 助手在本轮开头声明 `done`，**When** 本轮收尾，**Then** 系统不发出任何自救提醒，轮次正常关闭。
2. **Given** 助手在本轮开头声明 `awaiting_user`，**When** 本轮收尾，**Then** 系统不发出任何自救提醒，轮次正常关闭并等待用户。
3. **Given** 助手在本轮开头声明 `done`，**When** 本轮尚未收尾，**Then** 声明已记录在当前轮次下，后续收尾判定读到同一份状态。

---

### User Story 2 - 声明与判定使用同一轮次标识 (Priority: P1)

助手在某轮任意时刻调用声明工具，声明的归属轮次与该轮收尾判定使用的轮次始终一致；不存在"两个坐标系"。

**Why this priority**: 与 US1 同源。只要坐标不一致，任何时刻的声明都可能落空，且症状随调用时机漂移，极难复现和归因。

**Independent Test**: 在同一轮的多个不同时刻（轮次开始、工具调用中途、收到提醒之后）分别声明，确认每次返回的轮次号都等于本轮轮次，且收尾判定都能读到。

**Acceptance Scenarios**:

1. **Given** 本轮为第 N 轮，**When** 助手在轮次开头声明，**Then** 工具报告的轮次为 N。
2. **Given** 本轮为第 N 轮，**When** 助手在收到提醒后再声明，**Then** 工具报告的轮次仍为 N。
3. **Given** 上一轮为第 N-1 轮，**When** 新一轮开始后助手立即声明，**Then** 工具不得报告 N-1 或 0。

---

### User Story 3 - 缺陷可被自动化重现 (Priority: P2)

维护者改动轮次相关代码时，能在不启动真实会话的前提下，用自动化测试证明"主动声明会被尊重"。

**Why this priority**: 该缺陷在有真实会话前完全不可见（全部 47 项测试通过）。没有回归测试，同样的坐标错位会被再次引入。

**Independent Test**: 在测试中模拟"先声明、后收尾"的顺序，断言不产生注入；去掉修复后该测试必须失败。

**Acceptance Scenarios**:

1. **Given** 一个模拟轮次，其中助手在收尾前声明完成，**When** 触发收尾判定，**Then** 断言没有注入发生。
2. **Given** 同一测试在未修复的实现上运行，**When** 执行，**Then** 测试失败并指出声明未被识别。

---

### Edge Cases

- 插件刚加载、尚未观察到任何轮次事件时，助手立即调用声明工具：必须得到一个确定的轮次号，而不是哨兵值 `0`。
- 一轮内多次声明（先 `awaiting_user` 后 `done`）：后者覆盖前者，且仍归属于同一轮次。
- 上一轮声明了 `done`，新一轮开始：不得沿用上一轮的声明，新一轮必须重新判定。
- 宿主在同一轮内多次派发收尾判定（例如注入后又收尾一次）：轮次号必须保持稳定，不得随派发次数漂移。
- 声明工具在非顶层 agent（子 agent）中被调用：行为与「只对顶层生效」的既有约束保持一致。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 声明工具 MUST 报告"调用发生的那一轮"的轮次号，不得为哨兵值或上一轮的残留值。
- **FR-002**: 声明 MUST 写入该轮次的判定状态，使收尾判定在同一轮内能读到。
- **FR-003**: 收尾判定与声明工具 MUST 使用同一个轮次标识来源，不得各自推算。
- **FR-004**: 一轮内后声明 MUST 覆盖前声明，且不得改变轮次归属。
- **FR-005**: 轮次变化时，上一轮的声明 MUST NOT 被新一轮继承。
- **FR-006**: 插件尚未观察到任何轮次事件时，声明工具 MUST 给出确定行为（要么拒绝并说明原因，要么以可判定方式归属到即将开始的轮次），不得静默写入哨兵键。
- **FR-007**: 修复 MUST 附带可自动运行的回归测试，且该测试在未修复实现上失败。
- **FR-008**: 修复 MUST NOT 改变既有的三种状态语义（进行中 / 完成 / 等待用户）与其抑制注入的规则。

### Key Entities

- **轮次标识（Turn Key）**: 标识"这是哪一轮"的值，声明与判定都必须以它为键。
- **轮次状态（Turn Latch）**: 某一轮的目标状态与已发提醒次数；随轮次标识变化而整体更换。
- **声明（Declaration）**: 助手显式给出的目标状态，是插件判定"是否完成"的唯一依据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在真实会话中，助手在轮次开头声明 `done` 或 `awaiting_user` 后收尾，注入次数为 0（当前为 1）。
- **SC-002**: 同一轮的任意时刻声明，工具报告的轮次号与该轮收尾判定的轮次号一致，一致率 100%。
- **SC-003**: 回归测试在未修复实现上失败、在修复后通过，两者均可在仓库测试命令下复现。
- **SC-004**: 既有 47 项测试全部保持通过，无行为回归。
- **SC-005**: 因该缺陷产生的"每轮必催一次"现象消失：连续 3 轮主动声明后，注入总数仍为 0。

## Assumptions

- 宿主在工具调用发生前，已经能够提供当前轮次的标识（该信息在既有的流式帧里出现过，实现阶段需核实其可达性）。
- 轮次编号在一次会话内单调递增，且对同一个 agent 稳定。
- 缺陷二（上一轮收尾时监听器未运行）与本规格分开处理：它影响的是"插件何时开始观察"，不是"声明写到哪个键"。本规格只在需要时记录其证据，不把修复范围扩大。
- 该修复不引入新的持久化状态：轮次状态仍只存内存，进程重启后从零开始。
