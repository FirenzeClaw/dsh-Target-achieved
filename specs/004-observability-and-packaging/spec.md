# Feature Specification: 可观测性与可分发性

**Feature Branch**: `004-observability-and-packaging`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "/speckit-specify 004，并同期设计可在设置页面显示的配置入口，了解 DSHplugin 第三方插件市场的规范，本插件可按此规范插件化"

本规格把三件互相关联的事收进一个特性：**让插件的判定行为可观测、让它的配置可在设置页操作、让它可以按 DSH 插件市场规范发布与安装**。三者共享同一个前提——插件得先像一个"正规插件"那样存在，而不是一个靠手工改 profile 挂上去的私有包。

## 背景

### 为什么需要可观测性

2026-11-05 的一次误判：维护者看到"某轮结束时没有注入"，据此判定"收尾判定没运行"，并开出一份规格。解出会话日志后才发现那一轮结束于插件加载之前。

真正的问题是三种情况**外部表现完全相同**：

- 判定通过（已声明）→ 无注入
- 判定未运行（宿主未派发）→ 无注入
- 插件未加载 → 无注入

维护者只能靠"有没有注入"反推，而这个信号在"已声明"和"未运行"之间没有分辨力。

### 为什么需要设置页入口

当前 `enabled` 虽是 volatile 字段，但整条配置只存在于 profile 的 YAML 里。用户要关闭插件或调整阈值，得手改 `cordis.patch.yml` 再重启——这与插件作为"可安装产品"的定位不符。

### 为什么需要按市场规范插件化

当前包名为 `dsh-target-monitor`，`private: true`，只能通过 `link:` 手工挂载。要进入社区市场（DSH Plugin Hub）被搜索、安装、升级，必须满足官方 bundle 规范与市场清单格式。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每次判定都留下可查记录 (Priority: P1)

维护者想知道"这一轮到底有没有被判定"，能直接查到一条记录，而不是靠有没有注入去猜。

**Why this priority**: 这是本特性的起点。没有它，任何"门没生效"的报告都无法被证实或证伪。

**Independent Test**: 触发一次收尾判定，确认产生一条记录，内容足以还原这次判定。

**Acceptance Scenarios**:

1. **Given** 助手未声明就收尾，**When** 判定执行，**Then** 记录包含轮次、结果（注入）、原因（未声明）。
2. **Given** 助手已声明后收尾，**When** 判定执行，**Then** 记录包含轮次、结果（放行）、原因（已声明）。
3. **Given** 配置关闭或该 agent 非顶层，**When** 判定执行，**Then** 记录写明是哪一个原因导致放行。

---

### User Story 2 - 区分"没判定"与"判定通过" (Priority: P1)

当某一轮完全没有记录时，维护者能确信这是"判定没有运行"，而不是"运行了但没注入"。

**Why this priority**: 与 US1 构成一对。只有"有记录"与"无记录"含义互斥，记录才有诊断价值。

**Independent Test**: 构造一次不触发判定的情形，确认该轮没有任何判定记录。

**Acceptance Scenarios**:

1. **Given** 插件未加载的轮次，**When** 按轮次查询记录，**Then** 查不到该轮记录，且能据此判断"未判定"。
2. **Given** 插件已加载但宿主未派发的轮次，**When** 查询，**Then** 同样无记录，与上一种情形一致地表达"未判定"。

---

### User Story 3 - 在设置页开关与调阈值 (Priority: P1)

用户打开设置页，能直接看到本插件的开关与阈值，改动即时生效，无需编辑配置文件、无需重启。

**Why this priority**: 这是"插件"与"手工挂载的私有包"之间最直观的差别。没有它，用户每次调整都要碰 YAML。

**Independent Test**: 在设置页把开关关掉，确认同一轮内判定立刻停止注入；再打开，确认恢复。

**Acceptance Scenarios**:

1. **Given** 插件已安装并出现在设置页，**When** 用户关闭总开关，**Then** 后续判定不再注入，且无需重启。
2. **Given** 用户把阈值从 5 改为 2，**When** 下一轮连续两次未声明，**Then** 第 2 次即出现卡住提示。
3. **Given** 用户填写了非法阈值（0、负数、小数），**When** 保存，**Then** 被拒绝并给出明确原因，配置保持原值。
4. **Given** 插件运行中设置服务不可用，**When** 插件加载，**Then** 插件照常工作，只是设置页入口不可用——不得因为设置页缺席而拒绝启动。

---

### User Story 4 - 可按市场规范发布与安装 (Priority: P2)

维护者能把这个包发布成符合 DSH bundle 规范的插件，用户能从社区市场搜索到、一键安装、收到升级提示。

**Why this priority**: 决定插件能否被他人使用。优先级低于前三者，因为功能正确性先于分发。

**Independent Test**: 用市场读取端校验本包的清单条目，确认能通过格式校验并给出可安装目标。

**Acceptance Scenarios**:

1. **Given** 本包的 `package.json`，**When** 按 DSH bundle 规范检查，**Then** 声明了清单版本与 bundle 补丁路径，可被当作可安装 bundle。
2. **Given** 一条符合市场清单格式的条目，**When** 校验器读取，**Then** 通过校验，且安装目标为确定的版本。
3. **Given** 宿主版本不满足声明的兼容范围，**When** 用户查看市场条目，**Then** 条目标注为不兼容，而不是安装后崩溃。

---

### Edge Cases

- 判定在 `apply` 完成前到达：无记录即"未判定"，不得补写伪造记录。
- 同一轮内多次判定（注入后又收尾）：每次各留一条，顺序可辨。
- 长会话：记录不得无限增长，需明确的保留策略。
- 进程重启：历史记录是否跨重启保留需明确（默认不保留）。
- 多会话并发：记录必须能按会话/agent 区分。
- 设置页写入与命令行/家目录覆盖冲突：以更高优先级的覆盖为准，设置页写入被拒绝并说明。
- 插件以只读方式安装（无 profile 写入权限）：设置页入口降级为不可用，插件主体仍工作。
- 市场条目声明的版本与包实际版本不一致：属发布方错误，读取端不负责纠正，但安装目标必须指向确定版本。

## Requirements *(mandatory)*

### Functional Requirements

**留痕**

- **FR-001**: 每次收尾判定 MUST 产生一条记录，至少包含：轮次号、结果（注入/放行）、结果原因。
- **FR-002**: 结果原因 MUST 能区分"已声明"、"配置关闭"、"非顶层 agent"、"取消/错误"、"未声明"。
- **FR-003**: 记录 MUST NOT 进入模型可见面（对话消息、系统提示词、工具结果）。
- **FR-004**: 记录 MUST 可按轮次检索；查不到记录即表示该轮未被判定。
- **FR-005**: 记录 MUST 有明确的保留策略（条数或时间上限），不得无界增长。
- **FR-006**: 记录 MUST 能区分不同会话/agent。
- **FR-007**: 留痕失败 MUST NOT 影响判定本身。

**设置页**

- **FR-008**: 总开关与阈值 MUST 作为可在设置页编辑的字段暴露，且改动无需重启即生效。
- **FR-009**: 设置页 MUST 拒绝非法阈值并说明原因，不得静默回退默认值。
- **FR-010**: 设置服务缺席时，插件 MUST 照常完成判定，不得因设置页不可用而拒绝加载。
- **FR-011**: 设置页写入 MUST 遵守宿主的配置优先级；被更高优先级覆盖时，写入被拒绝并说明。

**可分发**

- **FR-012**: 包 MUST 声明 DSH 清单版本与 bundle 补丁路径，使其可被安装器识别为 bundle。
- **FR-013**: 包 MUST 声明其兼容的宿主版本范围，供市场与安装器判断兼容性。
- **FR-014**: 包 MUST 移除阻止发布的私有标记，并提供市场清单所需的展示元数据（名称、描述、分类、关键词）。
- **FR-015**: 包 MUST 声明其运行时依赖的宿主包，避免在用户环境里重复安装或版本冲突。
- **FR-016**: 本特性 MUST NOT 改变既有的判定语义（三种状态、注入预算、取消不复活）。

### Key Entities

- **判定记录**: 一次收尾判定的痕迹（时间、轮次、结果、原因、agent 标识）。
- **设置字段**: 用户在设置页可见可改的配置项（总开关、卡住提示阈值）。
- **包清单**: 描述包身份、兼容范围与 bundle 入口的元数据。
- **市场条目**: 市场清单中描述本插件的一个版本（版本号、发布时间、安装源、兼容范围、展示元数据）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 给定任意一轮，维护者能在一次查询内回答"这一轮有没有被判定"，无需查看对话内容。
- **SC-002**: 对"插件未加载"的轮次，查询结果能明确表达"未判定"，不产生误导。
- **SC-003**: 开启留痕前后，模型收到的消息与系统提示词逐字一致，token 数不变。
- **SC-004**: 连续 100 次判定后，记录总量不超过既定上限。
- **SC-005**: 用户从设置页关闭开关到注入停止，延迟不超过一轮；无需重启。
- **SC-006**: 本包的清单条目能通过市场格式校验，且安装目标指向确定版本。
- **SC-007**: 既有 53 项测试保持通过；新增能力各有对应测试。

## Assumptions

- 留痕面向本机维护者，不需要远程上报、不需要持久化到磁盘。
- 查询入口可以是工具、日志文件或调试命令；形态留到 plan 阶段决定。
- 设置页字段通过宿主的设置服务暴露；具体是否需要自绘页面，取决于宿主是否已能自动生成表单。
- 发布渠道为 npm（`name@version`）与 Git（commit 固定）二选一，或两者都提供；由 plan 阶段结合发布流程决定。
- 不引入新的运行时依赖。

## 与既有规格的关系

- 001 定义判定语义，本特性不改变它。
- 002 修的是轮次键错位；留痕记录的轮次号沿用同一来源。
- 003 已撤销（缺陷不成立）。本特性源自那次误判暴露的可观测性缺口，但范围收敛为留痕，不含"加载后首轮"这类未证实的假设。
