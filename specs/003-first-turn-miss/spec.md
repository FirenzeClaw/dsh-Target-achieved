# Feature Specification: 加载后首个收尾判定不触发

**Feature Branch**: `003-first-turn-miss`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "已重启，确认是否已引入"（实测发现插件加载后的**第一次**收尾判定没有触发，第二次才生效；要求开 003 号规格固定这个缺陷。）

## 背景与缺陷证据

2026-11-05 会话实测（宿主 0.2.1-rc.5，插件经 `link:` 挂在 web profile）：

| 时间 | 事件 | 观测 |
|---|---|---|
| 11:53:23 | `dsh web` 重启，插件加载成功（`target_status` 进入工具注册表） | 加载本身正常 |
| 11:54–11:56 | 第 3 轮：助手收尾时**未**声明目标状态 | **没有注入**（按设计应注入 attempt 1） |
| 11:59 | 第 4 轮开头调用 `target_status` | 返回 `turn: 0`，说明 `agent/turn-stopping` 监听器此前**一次都没运行过** |
| 12:00 | 第 4 轮收尾（仍未声明） | 注入到达（attempt 1）——监听器此时才第一次运行 |
| 13:25:57 | 再次重启（加载 spec 002 的轮次修复） | `assistant-stream` 的 `start` 帧**立即**被观察到（工具返回 `turn: 6`） |
| 13:29 | 第 6 轮收尾 | 已声明 `awaiting_user`，无注入；**因此无法判定监听器是否运行** |

**结论边界（必须保留）**：

- 已确认：11:53 那次加载后，第一轮收尾判定没有运行，第二轮才运行。
- 未确认：13:25 那次加载后 `turn-stopping` 是否同样漏掉第一轮——因为该轮已声明，漏与不漏都表现为"无注入"，观测不可区分。
- 因此本规格不声称"每次加载必然漏第一轮"，只声称"存在加载后漏掉首轮的情形，且当前无法从外部观测到它是否发生"。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 加载后的第一轮就受门控 (Priority: P1)

运维重启服务后，助手在**第一个**轮次里就该受到收尾门保护。用户不应遇到"重启后的第一次对话没有被保护、第二次才正常"这种时好时坏的行为。

**Why this priority**: 收尾门的全部价值在于不遗漏。漏掉一轮意味着用户可能正好在那一轮遇到静默中断，而这种遗漏没有任何外在征兆。

**Independent Test**: 重启插件（或重新加载）后，构造一个"未声明就收尾"的轮次，确认注入照常发生。

**Acceptance Scenarios**:

1. **Given** 插件刚加载完成、尚未处理过任何轮次，**When** 助手第一次未声明就收尾，**Then** 系统照常注入自救提醒。
2. **Given** 同样刚加载的状态，**When** 助手第二次未声明就收尾，**Then** 行为与第一次一致。

---

### User Story 2 - 漏判时可被观测 (Priority: P1)

当收尾判定没有如期运行时，维护者能从日志或诊断信息中看出"这一轮没有被判定"，而不是只能靠"有没有收到注入"去反推——后者在已声明的情况下完全不可区分。

**Why this priority**: 当前缺陷之所以难定位，正是因为"判定跑了但通过"与"判定根本没跑"在外部表现完全相同。缺少可观测性，同类问题只能靠偶遇。

**Independent Test**: 构造一次未触发的收尾判定，确认存在一条可查询的记录（日志或诊断计数）。

**Acceptance Scenarios**:

1. **Given** 插件已加载并订阅了收尾事件，**When** 宿主派发一次收尾判定，**Then** 插件留下一条可追溯的记录（轮次、是否注入、原因）。
2. **Given** 插件已加载但宿主从未派发收尾判定，**When** 维护者检查诊断信息，**Then** 能区分"没有派发"与"派发且通过"。

---

### User Story 3 - 缺陷可被自动化重现 (Priority: P2)

维护者改动插件加载或事件订阅相关代码时，能用一个自动化测试证明"加载后的第一轮同样受门控"。

**Why this priority**: 该缺陷只在真实进程的加载时序下出现，现有 53 项测试全部通过却完全覆盖不到。

**Independent Test**: 在不启动真实会话的前提下模拟"刚加载 → 第一轮收尾"，断言注入发生。

**Acceptance Scenarios**:

1. **Given** 一个模拟的加载过程，其中插件刚 `apply`、尚未处理任何轮次，**When** 触发第一次收尾判定，**Then** 断言注入发生。
2. **Given** 同一测试在存在漏判的实现上运行，**When** 执行，**Then** 测试失败并指出首轮未被判定。

---

### Edge Cases

- 会话在插件加载**之前**就已存在（resume 场景）：加载后的第一个轮次仍须受门控。
- 插件热重载（配置变更触发重新 `apply`）后，后续轮次不得出现空窗。
- 同一进程内多个会话并发：一个会话的首轮漏判不得影响其他会话。
- 宿主在加载完成前就派发了收尾判定：插件要么处理，要么留下明确记录，不得静默丢弃。
- 收尾判定在插件 `apply` 尚未完成时到达：需要明确"此时订阅是否已经建立"。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 插件完成加载后的**第一个**收尾判定 MUST 与后续轮次行为一致（未声明即注入）。
- **FR-002**: 插件 MUST NOT 依赖"至少有一轮已经跑过"才能生效。
- **FR-003**: 每当收尾判定被处理，插件 MUST 留下可追溯记录，至少包含轮次号与是否注入。
- **FR-004**: 当收尾判定**未被处理**（宿主未派发，或派发时插件尚未就绪），插件的诊断信息 MUST 能让维护者区分这两种情况。
- **FR-005**: 修复 MUST 附带可自动运行的回归测试，且该测试在未修复实现上失败。
- **FR-006**: 修复 MUST NOT 改变既有判定语义（三种状态、注入预算、取消不复活）。

### Key Entities

- **加载完成时刻**: 插件 `apply` 返回、订阅建立的时点。
- **首个收尾判定**: 加载完成后宿主第一次派发的 `agent/turn-stopping`。
- **判定记录**: 每次判定处理的可追溯痕迹（轮次、注入与否、原因）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 重启服务后连续 3 轮未声明收尾，注入次数为 3（当前可能为 2）。
- **SC-002**: 任意一次收尾判定，都能在诊断信息中找到对应记录；"判定通过"与"未判定"可区分，歧义率 0。
- **SC-003**: 回归测试在未修复实现上失败、修复后通过。
- **SC-004**: 既有 53 项测试全部保持通过。

## Assumptions

- 宿主在加载完成后才会开始新的轮次；跨加载的进行中轮次不在本规格范围（已由 spec 001 的取消语义覆盖）。
- 缺陷根因尚未确定，候选方向：订阅建立的先后顺序、agent 作用域过滤、宿主在该轮未派发事件。本规格只约束行为，不预设实现。
- 修复不引入持久化诊断存储；进程内可查询即可。

## 与 spec 001 / 002 的关系

- 001 定义了"未声明即注入"的产品行为，本规格保证该行为在**加载后的第一轮**同样成立。
- 002 修的是"声明写到错误的轮次键"，与本规格的"判定根本没运行"是两个独立缺陷：前者是坐标系错位，后者是事件未到达。
