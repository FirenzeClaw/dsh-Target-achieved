# Feature Specification: 收尾判定留痕

**Feature Branch**: `004-gate-trace`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "把'判定留痕'另开一条"（在一次误判之后提出：当时无法从外部区分"判定跑了但通过"与"判定根本没跑"，导致把一个不存在的缺陷当成真缺陷排查了近一小时。）

## 背景：这次误判是怎么发生的

2026-11-05，维护者看到"某轮结束时没有收到注入"，据此判断"收尾判定没有运行"，进而开出一份规格。解出会话日志后才发现：那一轮结束于插件加载之前，根本不在门控范围内。

真正的问题不是那次误判本身，而是**插件没有留下任何"我判定过"的痕迹**：

- 判定通过（已声明）→ 无注入
- 判定未运行（宿主未派发）→ 无注入
- 插件未加载 → 无注入

三种情况的**外部表现完全相同**。维护者只能靠"有没有注入"反推，而这个信号在"已声明"和"未运行"之间没有分辨力。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每次判定都留下可查记录 (Priority: P1)

维护者想知道"这一轮到底有没有被判定"，能直接查到一条记录，而不是靠有没有注入去猜。

**Why this priority**: 这是本特性的全部理由。没有它，任何"门没生效"的报告都无法被证实或证伪。

**Independent Test**: 触发一次收尾判定，确认产生一条记录，内容足以还原这次判定。

**Acceptance Scenarios**:

1. **Given** 助手未声明就收尾，**When** 判定执行，**Then** 记录包含轮次、判定结果（注入）、注入原因。
2. **Given** 助手已声明后收尾，**When** 判定执行，**Then** 记录包含轮次、判定结果（放行）、放行原因（已声明）。
3. **Given** 配置关闭或该 agent 非顶层，**When** 判定执行，**Then** 记录写明是哪一个原因导致放行。

---

### User Story 2 - 区分"没判定"与"判定通过" (Priority: P1)

当某一轮完全没有记录时，维护者能确信这是"判定没有运行"，而不是"运行了但没注入"。

**Why this priority**: 与 US1 构成一对。只有"有记录"和"无记录"的含义互斥，记录才有诊断价值。

**Independent Test**: 构造一次不触发判定的情形，确认该轮没有任何判定记录，且这一缺失本身可被查询到（例如按轮次检索为空）。

**Acceptance Scenarios**:

1. **Given** 插件未加载的轮次，**When** 维护者按轮次查询记录，**Then** 查不到该轮记录，且能据此判断"未判定"。
2. **Given** 插件已加载但宿主未派发的轮次，**When** 查询，**Then** 同样无记录，与上一种情形一致地表达"未判定"。

---

### User Story 3 - 记录不污染用户可见内容 (Priority: P1)

留痕只给维护者看，不出现在对话里、不进入模型上下文、不改变 token 消耗。

**Why this priority**: 本插件已经因为"会自己说话"而敏感。诊断信息一旦进入模型可见面，就等于给注入面开了个后门，违反项目宪法原则 III。

**Independent Test**: 触发若干次判定，确认模型收到的消息与不开启留痕时完全一致。

**Acceptance Scenarios**:

1. **Given** 留痕开启，**When** 判定执行多次，**Then** 会话中不新增任何消息，模型上下文的 token 数不变。
2. **Given** 留痕开启，**When** 检查系统提示词，**Then** 内容与关闭时一致。

---

### Edge Cases

- 判定在 `apply` 完成前到达：无记录即为"未判定"，不得补写一条伪造记录。
- 同一轮内多次判定（注入后又收尾）：每次各留一条，顺序可辨。
- 长会话：记录不得无限增长到影响内存或启动时间，需要明确的保留策略。
- 进程重启：历史记录是否需要跨重启保留，需在规格中明确（默认不保留）。
- 多个会话并发：记录必须能按会话/agent 区分，不得混在一起。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每次收尾判定 MUST 产生一条记录，至少包含：轮次号、判定结果（注入/放行）、结果原因。
- **FR-002**: 结果原因 MUST 能区分"已声明"、"配置关闭"、"非顶层 agent"、"取消/错误"、"未声明"。
- **FR-003**: 记录 MUST NOT 进入模型可见面（对话消息、系统提示词、工具结果）。
- **FR-004**: 记录 MUST 可按轮次检索；查不到记录即表示该轮未被判定。
- **FR-005**: 记录 MUST 有明确的保留策略（条数或时间上限），不得无界增长。
- **FR-006**: 记录 MUST 能区分不同会话/agent。
- **FR-007**: 留痕失败 MUST NOT 影响判定本身（写记录出错时照常注入或放行）。
- **FR-008**: 该特性 MUST 有回归测试覆盖，且测试不依赖真实会话。

### Key Entities

- **判定记录**: 一次收尾判定的痕迹（时间、轮次、结果、原因、agent 标识）。
- **保留策略**: 记录的最大条数或最长保留时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 给定任意一轮，维护者能在一次查询内回答"这一轮有没有被判定"，无需查看对话内容。
- **SC-002**: 对同一次误判场景（插件未加载的轮次），查询结果能明确表达"未判定"，不产生误导。
- **SC-003**: 开启留痕前后，模型收到的消息与系统提示词逐字一致，token 数不变。
- **SC-004**: 连续 100 次判定后，记录总量不超过既定上限。
- **SC-005**: 既有 53 项测试保持通过。

## Assumptions

- 留痕面向本机维护者，不需要远程上报、不需要持久化到磁盘。
- 查询入口可以是工具、日志文件或调试命令；具体形态留到 plan 阶段决定。
- 不引入新依赖。
- 该特性不改变任何现有判定行为，只增加旁路记录。

## 与既有规格的关系

- 001 定义判定语义，本特性不改变它。
- 002 修的是轮次键错位；本特性不依赖它，但记录的轮次号沿用同一来源。
- 003 已撤销（缺陷不成立），本特性源自那次误判暴露的可观测性缺口，与 003 的原始诉求部分重叠，但范围收敛为"留痕"，不含"加载后首轮"这类未证实的假设。
