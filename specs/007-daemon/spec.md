# Feature Specification: 跨进程监测守护

**Feature Branch**: `007-daemon`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: 「升级为随 DSH 启动的单进程、多 session 监听、随 DSH 关闭释放、多 DSH 联合监测与父进程转让」；设计评审补充「不能做单纯空闲回收，会话有保留价值」「将进程独立的方案提升为类似 mcp 的真实单一主进程」「脱离式守护进程 + 连接计数（因此不需要父进程转让）」

## 背景与问题

当前实现是**插件形态**：每个 DSH 进程里的 cordis 插件各持一份状态，全部存在 `WeakMap<Agent, …>` 里（`src/state.ts`、`src/forget.ts`、`src/resume.ts`、`src/turn.ts`）。这有三个直接后果：

1. **计数不共享**：`web`（3080）、CLI、临时验证实例各有一份「遗忘次数」与「续行次数」。用户在不同入口之间切换时，同一个任务的累计次数被反复清零，阈值永远到不了。
2. **留痕存在并发写**：`$DSH_HOME/logs/target-monitor/gate-trace.jsonl` 是共享路径，多个进程同时 `appendFileSync` 时，超过 `PIPE_BUF` 的行可能交错，事后按 JSON 解析会失败。
3. **进程退出即失忆**：重启 DSH 之后，所有累计计数归零。

本规格把「状态与判定」搬到一个**独立的守护进程**里，DSH 侧的插件退化为瘦客户端：它只负责把事件转发给守护进程、并执行返回的注入决定。

明确的非目标：不做**空闲会话回收**（会话有保留价值，用户可能数小时后回来）；不做**跨机器**同步；不做**父进程转让**（脱离式启动 + 连接计数已经覆盖生命周期需求）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多个 DSH 实例共享同一份判定 (Priority: P1)

用户同时开着 web 界面和一个 CLI 会话，两边都在做同一件事。web 这边因为忘记声明被提醒了两次；切到 CLI 继续做，第三次忘记声明时，CLI 侧直接带上了规范复述——因为计数是跨进程累计的。

**Why this priority**: 这是本规格存在的核心理由。计数不共享时，阈值形同虚设；用户看到的是「两个入口各提醒一次，永远等不到复述」。

**Independent Test**: 同时启动两个 DSH 进程（不同端口），在两侧交替让轮次以「未声明」结束，观察第二次提醒是否带复述（阈值 3 时，第 3 次注入才带）。仅靠单进程无法验证。

**Acceptance Scenarios**:

1. **Given** 守护进程已运行且两个 DSH 都已连接，**When** 进程 A 记录一次未声明注入，**Then** 进程 B 的下一次判定能读到累计后的计数。
2. **Given** 两个 DSH 同时产生留痕，**When** 事后按行解析留痕文件，**Then** 每一行都是合法 JSON，不出现截断或交错。
3. **Given** 同一会话在进程 A 声明了 `done`，**When** 该会话在进程 B 的同一轮次再次判定，**Then** 读到的是已声明状态而不是全新的未声明状态。

---

### User Story 2 - 生命周期跟随 DSH，但不打断正在进行的会话 (Priority: P2)

用户启动第一个 DSH 时，守护进程被自动拉起；之后随便开多少个 DSH 都复用它。用户关掉最后一个 DSH 后，守护进程再等 30 秒确认没人回来，然后自己退出，不留残余 socket。若上一个守护进程被强杀留下陈旧 socket，下次启动能自愈。

**Why this priority**: 决定它能不能长期驻留而不成为负担。没有自动退出，用户机器上会长期挂一个多余进程；没有自愈，一次崩溃会让后续所有启动都连不上。

**Independent Test**: 启动 DSH → 确认守护进程存在；关闭 DSH → 30 秒后确认进程已退出且 socket 文件已删除；手动 `kill -9` 守护进程留下 socket 再启动 → 确认能自愈。

**Acceptance Scenarios**:

1. **Given** 机器上没有任何 DSH 在跑且没有守护进程，**When** 第一个 DSH 启动并加载插件，**Then** 守护进程被拉起，客户端在 5 秒内连接成功。
2. **Given** 守护进程已连接两个 DSH，**When** 其中一个退出，**Then** 守护进程继续运行，另一个的功能不受影响。
3. **Given** 最后一个 DSH 已退出，**When** 30 秒内没有新连接，**Then** 守护进程退出并删除 socket 与 pid 文件。
4. **Given** 守护进程被强杀、socket 文件残留，**When** 新的 DSH 启动，**Then** 客户端识别出 socket 不可用、清理残留并重新拉起守护进程。

---

### User Story 3 - 守护进程不可用时，功能不丢 (Priority: P3)

守护进程因为权限、端口占用或未知原因起不来。插件的所有既有能力仍然可用：收尾门照常判定、照常注入、照常留痕——只是计数不再跨进程共享，留痕改为本地写。

**Why this priority**: 守护进程是新引入的故障面。没有降级路径，一个后台进程的问题会直接让插件整体失效——比它要解决的问题更糟。

**Independent Test**: 强制让守护进程无法启动（例如把 socket 路径指向不可写目录），观察插件是否仍能正常拦截并注入，且留痕仍能写入。

**Acceptance Scenarios**:

1. **Given** 守护进程无法启动，**When** 轮次在未声明状态下结束，**Then** 插件仍然注入自救提醒，行为与引入守护进程前一致。
2. **Given** 已降级为进程内判定，**When** 查看留痕，**Then** 记录中带有降级标记，能区分这条是本地判定产生的。
3. **Given** 单次请求超过 200 毫秒未返回，**When** 客户端等待超时，**Then** 立即降级为该次判定的本地执行，不阻塞轮次收尾。

---

### Edge Cases

- **同一台机器上存在多个 `DSH_HOME`**：socket 与 pid 文件都落在各自的 `DSH_HOME` 下，互不干扰；不同 `DSH_HOME` 之间不共享状态。
- **守护进程与客户端版本不一致**（插件升级后旧守护进程还在跑）：握手时协议版本不匹配，客户端拒绝使用该守护进程，转为降级模式并告警一次。
- **socket 文件存在但无人监听**（上次异常退出）：连接立即失败，按 US2 场景 4 自愈。
- **权限不足**（`$DSH_HOME/run` 不可写）：记一条告警，进入降级模式，不反复重试。
- **磁盘写满**：留痕写入失败只告警一次，不影响判定与注入。
- **守护进程收到未知请求或畸形 JSON**：返回错误响应，不退出进程。
- **同一 `(sessionId, turn)` 的重复请求**（客户端重发）：按幂等处理，不重复计数。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 守护进程 MUST 作为独立进程运行，通过 unix domain socket 提供服务，socket 路径为 `$DSH_HOME/run/target-monitor.sock`，文件权限 `0600`。
- **FR-002**: DSH 侧插件 MUST 在首次请求前检查连接；无可用连接时以 `detached` 方式拉起守护进程，并以 50 毫秒间隔重试连接，总上限 5 秒。
- **FR-003**: 客户端与守护进程 MUST 在连接建立后立即握手，交换协议版本与客户端标识；版本不匹配时客户端 MUST 放弃使用该守护进程。
- **FR-004**: 守护进程 MUST 维护连接计数；最后一个连接断开后启动 30 秒宽限计时，期间无新连接则退出，并删除 socket 与 pid 文件。
- **FR-005**: 守护进程 MUST 是判定状态的唯一权威，持有遗忘计数、待判定时间戳、续行计数、当日声明状态；客户端 MUST NOT 在本地保存这些状态（降级期间除外）。
- **FR-006**: 客户端 MUST 在每次请求中携带当前配置快照；守护进程 MUST NOT 读取宿主配置，也 MUST NOT 持久化配置。
- **FR-007**: 守护进程 MUST 按 `(sessionId, agentId)` 隔离状态，同一进程内多个 agent、不同进程的同名会话 MUST NOT 互相污染。
- **FR-008**: 守护进程 MUST 是留痕的唯一写入口；并发写入时 MUST 保证每条记录独占一行且为合法 JSON。
- **FR-009**: 守护进程 MUST 只返回判定结果，不直接操作任何 agent；实际的注入与 `steer` MUST 由客户端在原进程内执行。
- **FR-010**: 单次请求超过 200 毫秒未返回时，客户端 MUST 立即降级为该次判定的本地执行，不得阻塞轮次收尾。
- **FR-011**: 降级期间的留痕 MUST 由客户端本地写入，并 MUST 在记录中标注降级标记。
- **FR-012**: 降级 MUST 只作用于当前进程的后续请求；同一进程内 MUST NOT 重复尝试拉起守护进程（避免每次轮次收尾都阻塞 5 秒），但新启动的进程 MAY 重新尝试。
- **FR-013**: 守护进程处理单个请求时的异常 MUST 被隔离，返回错误响应并继续服务，MUST NOT 退出进程。
- **FR-014**: 守护进程 MUST NOT 接收或存储会话正文、提示词或工具输出；请求只允许携带判定所需的元数据（轮次、声明状态、错误码、配置快照）。
- **FR-015**: 同一 `(sessionId, turn)` 的重复请求 MUST 按幂等处理，不重复计数、不重复写留痕。
- **FR-016**: 插件 MUST 提供一个配置项，强制使用进程内模式且不拉起守护进程，用于排查与受限环境。
- **FR-017**: 守护进程不可用时 MUST NOT 影响插件其余能力：收尾门判定、注入、`target_status` 工具、上游续行 MUST 全部保持可用。
- **FR-018**: 客户端 MUST 在守护进程不可用时只告警一次（按进程计），避免每次判定都刷日志。

### Key Entities

- **SessionBinding**: 一个客户端连接上的会话绑定，属性为 `sessionId`、`clientId`、`configSnapshot`、`connectedAt`。生命周期与连接一致。
- **MonitorState**: 某个 `(sessionId, agentId)` 的判定状态，属性为遗忘计数、待判定时间戳、续行连续次数、最后轮次号、当日声明状态。跨客户端共享。
- **TraceRecord**: 一条留痕，属性为时间、会话标识、轮次、判定结果、原因、错误码（可选）、是否降级。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 两个 DSH 进程交替产生未声明轮次时，第 3 次注入带上规范复述，与单进程连续 3 次的判定结果一致。
- **SC-002**: 关闭最后一个 DSH 后，守护进程在 30 秒（±2 秒）内退出，`$DSH_HOME/run/` 下不残留 socket 与 pid 文件。
- **SC-003**: 守护进程无法启动时，插件的注入与留痕成功率与引入前一致（回归测试全绿），且用户最多看到一条告警。
- **SC-004**: 两个进程同时产生留痕时，1000 条记录全部可按行解析为合法 JSON，零截断、零交错。
- **SC-005**: 守护进程不可用时，单次轮次收尾的额外耗时不超过 200 毫秒。
- **SC-006**: 强杀守护进程后重启 DSH，5 秒内恢复连接，无需人工清理文件。

## Assumptions

- 运行环境支持 unix domain socket（Linux 与 macOS）；Windows 使用命名管道，属后续工作。
- 一台机器上可能有多个 DSH 进程，但只有一个 `DSH_HOME`；不同 `DSH_HOME` 之间按独立部署处理。
- 守护进程与 DSH 使用同一份 Node 运行时，不需要兼容多种运行时版本。
- 留痕文件所在磁盘由用户负责；写满时只告警，不阻塞判定。
- 守护进程不参与权限、模型或 provider 决策，只做状态与判定。
