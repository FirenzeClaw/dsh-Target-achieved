# Phase 0 研究：跨进程监测守护

本文件记录 007 的技术未知项与结论。每条给出决定、依据与备选方案。

## R-001 传输：unix domain socket + 换行分隔 JSON

- **决定**：`net.createServer` 监听 unix socket 路径，协议为「一行一条 JSON」（NDJSON）。
- **依据**：Node 内置 `node:net`，无第三方依赖；单连接双向流，既能请求/响应也能服务端主动推送；本机 IPC 的标准形态（Docker、systemd、各类 daemon 均如此）。
- **备选**：HTTP over unix socket（需要自己解析请求行与头部，无收益）；共享文件 + 文件锁（Node 无内置 `flock`，只能靠 `mkdir` 自旋，错一次就是数据损坏）；TCP 端口（要处理端口冲突、跨用户访问控制）。

## R-002 双实现，而不是替换

- **决定**：抽 `Monitor` 接口，保留现有 `src/state.ts`、`src/forget.ts`、`src/resume.ts`、`src/turn.ts` 作为 `LocalMonitor`；新增 `RemoteMonitor` 走 socket。运行时按可用性选择。
- **依据**：FR-017 要求守护进程不可用时功能全在。直接替换等于删掉唯一的降级路径。
- **代价**：两套实现要各自维护。用共享的类型与同一组契约测试压住差异（见 quickstart 的「双实现一致性」检查）。

## R-003 拉起方式

- **决定**：`spawn(process.execPath, [daemonEntry], { detached: true, stdio: 'ignore' })` 然后 `child.unref()`；随后以 50 毫秒间隔重试连接，总上限 5 秒。
- **依据**：`detached` 让守护进程脱离父进程的会话与终端，父进程退出不会带走它；`stdio: 'ignore'` 避免父进程的管道被继承而无法关闭；`unref()` 让父进程的事件循环不被这个子进程拖住。
- **备选**：要求用户手动启动（违反 US2 场景 1）；用 systemd user unit（增加部署成本，且与「跟着 DSH 起停」的目标不符）。

## R-004 陈旧 socket 的识别与清理

- **决定**：连接失败的 `error.code` 分流——`ENOENT` 表示文件不存在（从未启动或已被清理）；`ECONNREFUSED` 表示文件在但无人监听（上次异常退出）。只有后者才进入清理流程，且清理前必须用 pid 文件做二次确认：`process.kill(pid, 0)` 抛 `ESRCH` 才能 `unlink`。
- **依据**：仅凭 `ECONNREFUSED` 就删文件存在竞态——守护进程刚 `bind` 完但还没 `listen` 的窗口里，另一个客户端会误判为陈旧。
- **备选**：直接 unlink 后重拉（偶发地把正在启动的守护进程打成孤儿）。

## R-005 生命周期：连接计数 + 30 秒宽限

- **决定**：守护进程维护连接数；归零后启动 `setTimeout(30_000)`，到期退出并清理 socket 与 pid；宽限期内出现新连接则取消计时。计时器必须 `unref()`。
- **依据**：用户常常关一个窗口就开另一个；立刻退出会导致频繁重启。`unref()` 是因为未清理的计时器会把「没有连接」的进程永久留住。
- **备选**：立即退出（抖动）；永驻（用户机器上多一个常驻进程，违反 US2 的初衷）。

## R-006 留痕单写

- **决定**：正常路径下只有守护进程写留痕；降级路径下由客户端本地写，并在记录里带 `degraded: true`。
- **依据**：守护进程单线程、逐条处理请求，写入天然串行，满足 FR-008。降级时没有并发保证，只能用标记把两类记录区分开。

## R-007 会话标识

- **决定**：状态键用 `agent.id`（`SessionId` 字符串）。
- **依据**：`dsh-agent/lib/types/types.d.ts:13` 声明 `readonly id: SessionId`；`dsh-agent/lib/types/runtime-types.d.ts:143` 另有 `readonly session: Session`。两者都在 agent 创建时确定，跨进程一致（同一会话被 ACP 恢复时沿用同一 id）。
- **备选**：用 `Agent` 对象引用做键（跨进程无意义）；用工作目录（同一目录可能开多个会话）。

## R-008 收尾门改为异步

- **决定**：`agent/turn-stopping` 监听器改为 `async`，`await` 守护进程响应；超时 200 毫秒后走本地兜底。
- **依据**：该钩子由 `dsh-agent-loop/lib/index.js:1001` 的 `this.dispatch.serial("agent/turn-stopping", ...)` 派发，serial 意味着宿主逐个 `await` 监听器；监听器返回前把消息压进 inbox，宿主随后检查 `nextStep`，注入仍然有效。
- **风险**：若未来宿主改成非 awaited 派发，异步监听器会来不及注入。缓解：超时分支与降级分支都走**同步**本地判定，保证最坏情况下仍有注入。

## R-009 协议版本

- **决定**：连接建立后客户端先发 `hello`，携带 `protocol` 整数与 `clientId`；守护进程在版本不匹配时回 `fatal` 并断开。
- **依据**：插件会被独立升级，而旧守护进程可能仍在运行（它不属于 npm 包的更新周期）。没有版本协商时，字段变化会表现为难以归因的静默错误。

## R-010 幂等键

- **决定**：每个请求带 `requestId`（`clientId` + 单调递增序号）；守护进程对 `(sessionId, turn, phase)` 记录已处理结果，同键重复请求直接返回缓存结果。
- **依据**：FR-015 要求幂等。真实触发场景是客户端超时重发——此时客户端并不知道第一次是否已经生效。

## R-011 测试策略

- **决定**：三层——(1) 单元：协议编解码、状态机、决策函数；(2) 集成：在临时 `DSH_HOME` 下 spawn 真实守护进程，覆盖连接、判定、退出、陈旧 socket；(3) 多进程：起两个客户端连接同一守护进程，验证计数共享。
- **依据**：仓库用 `node --test`，无测试框架依赖；临时目录避免污染真实 `~/.dsh`（004 已经踩过这个坑，`defaultDirForEnv()` 在 `NODE_TEST_CONTEXT` 下返回 `undefined`）。

## R-012 配置来源

- **决定**：客户端在每次请求里带配置快照；守护进程不读宿主配置、不持久化配置。
- **依据**：配置是 volatile 的，随时可能被用户在设置页改；让守护进程持有配置就必须实现推送与失效，等于把宿主已经解决的问题再做一遍。客户端本来就在事件发生的现场，取当前值最直接。
