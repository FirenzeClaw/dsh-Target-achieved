# Feature Specification: 目标达成监测器（收尾门）

**Feature Branch**: `001-target-monitor`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "为 DSH 设计目标达成插件：在对话过程中未达成目标时，能向对话自动注入 continue or done&report，防止思考泄露、输出格式化异常、上游连接不稳定中断导致的任务中断。插件在对话开始时向模型注入规范：任务完成并汇报前将 Target 监测器置为 done；监测器处于 done 时确认任务完成、不激活注入；下一轮对话启动时监测器自动切回 working。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 未声明完成即收尾时自动续行 (Priority: P1)

用户让助手完成一项需要多步操作的任务。助手在任务尚未完成、也没有说明卡在哪里的情况下结束了本轮。系统识别到"本轮未声明目标状态"并自动要求助手继续，用户在界面上看到任务被继续推进，而不是一个看似完成实则半途而废的结果。

**Why this priority**: 这是插件的存在理由。没有它，所有其他能力都失去意义；只有它也能独立交付价值（把静默中断变成继续推进）。

**Independent Test**: 构造一个"只做一半就收尾且不声明状态"的轮次，观察是否在同一轮内自动继续，且用户无需再次输入。

**Acceptance Scenarios**:

1. **Given** 助手本轮尚未声明目标状态，**When** 助手结束本轮，**Then** 系统自动发出一次自救提醒，本轮继续而不是关闭。
2. **Given** 系统已发出自救提醒，**When** 助手声明任务完成并汇报，**Then** 本轮正常关闭，不再发出提醒。
3. **Given** 系统已发出自救提醒，**When** 助手声明需要用户决策，**Then** 本轮正常关闭，不再发出提醒。

---

### User Story 2 - 等待用户确认时不被打扰 (Priority: P1)

助手在删除数据、覆盖文件等需要确认的操作前停下，向用户提问。系统识别这是"等待用户"而非"任务中断"，不催促助手继续，用户看到的是一个提问而不是被插件推着继续执行。

**Why this priority**: 与 P1 同等重要。若缺失，插件会把合法等待误判为中断并催促，性质等同于伪造用户授权，比中断本身更危险。

**Independent Test**: 构造一个"提问后收尾且声明等待用户"的轮次，确认不产生任何自动提醒。

**Acceptance Scenarios**:

1. **Given** 助手声明正在等待用户确认，**When** 本轮结束，**Then** 系统不发出任何自救提醒。
2. **Given** 助手已声明等待用户，**When** 用户回复后开启新一轮，**Then** 新一轮以"进行中"开始，收尾门照常生效。

---

### User Story 3 - 输出被截断时从中断处继续 (Priority: P2)

模型的输出触及长度上限被截断，后续本应发起的工具调用没有执行。系统识别"截断"这一具体原因，要求助手从中断处继续，并明确告知被截断之后的工具调用没有执行，避免助手误以为那些操作已完成。

**Why this priority**: 截断是最高频的真实故障之一，且误判代价高（未执行的写操作被当成已执行）。

**Independent Test**: 构造一次以长度上限结束的轮次，检查提醒内容是否说明"被截断"与"后续工具未执行"。

**Acceptance Scenarios**:

1. **Given** 本轮因输出长度上限结束且未声明状态，**When** 系统发出提醒，**Then** 提醒包含"输出被截断，截断后的工具调用未执行"的明确说明。
2. **Given** 本轮正常结束（非截断）且未声明状态，**When** 系统发出提醒，**Then** 提醒不包含截断相关表述。

---

### User Story 4 - 卡住时告知用户 (Priority: P2)

助手连续多次未声明状态，系统持续要求其继续但始终没有得到交代。达到阈值后，系统向用户展示一条提示，说明该轮已多次未声明完成、可能卡住，用户可以据此中断或介入。

**Why this priority**: 插件不设修复上限，因此必须有一个让用户知情的出口，否则可能无限消耗。

**Independent Test**: 构造连续 5 次未声明的轮次，确认第 5 次时出现面向用户的提示，且第 6 次及以后不再重复提示。

**Acceptance Scenarios**:

1. **Given** 同一轮内已连续 4 次未声明并收到提醒，**When** 第 5 次仍未声明，**Then** 系统向用户展示"可能卡住"的提示。
2. **Given** 用户已看到该提示，**When** 第 6 次仍未声明，**Then** 系统继续要求继续但不重复展示提示。

---

### User Story 5 - 用户取消优先于插件判断 (Priority: P3)

用户主动中断了正在进行的轮次。系统不再发出任何自救提醒，本轮就此结束；当用户再次输入开启新一轮时，收尾门自动恢复生效。

**Why this priority**: 尊重用户中断是底线；但由于宿主在取消路径上本就不会进入收尾判断，此项主要是防御性保证。

**Independent Test**: 在轮次进行中取消，确认不产生提醒；随后再次输入，确认新轮次正常受门控。

**Acceptance Scenarios**:

1. **Given** 用户在轮次进行中取消，**When** 本轮结束，**Then** 系统不发出任何自救提醒。
2. **Given** 用户取消后重新输入，**When** 新一轮开始，**Then** 收尾门对该轮照常生效。

---

### Edge Cases

- **子助手轮次**：子助手结束本轮时不触发收尾门，避免父与子互相催促；仅顶层对话受门控。
- **目标轮次自然完成**：由自主目标推进驱动的轮次在目标达成时结束，应视为已声明完成，不再催一次。若该判定所需的时序在宿主侧不可靠，允许退化为"最多多催一次"，但不得重复催促。
- **上游请求彻底失败**：请求重试耗尽后轮次以失败结束，此时不进入收尾判断；插件不得自行重启该轮。
- **提前声明又继续工作**：助手在轮次中途声明完成但随后继续操作，本轮内该声明持续有效；代价是可能漏判一次续行，接受此代价以保持语义简单。
- **同一轮多次未声明**：每次收尾都重新判断，提醒次数在同一轮内累计，跨轮次清零。
- **无任何工具调用就被截断**：不做"是否调用过工具"的豁免，仍按截断处理——轻微上下文腐化时模型可能在任何工具调用之前中断。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每个顶层对话轮次维护一个目标状态，取值为"进行中"（默认）、"已完成"、"等待用户"。
- **FR-002**: 系统 MUST 为模型提供声明目标状态的能力，声明需可归属到具体插件、可从对话记录回放。
- **FR-003**: 系统 MUST 在每轮开始时将目标状态置为"进行中"，无需任何显式重置动作。
- **FR-004**: 当轮次即将正常结束时，系统 MUST 检查该轮状态：已声明"已完成"或"等待用户"则放行；否则发出自救提醒并要求继续。
- **FR-005**: 自救提醒（Repair Notice，下同）MUST 通过模型可见、用户可见且带来源归属的通道投递，且不新增对话之外的通知组件。
- **FR-006**: 自救提醒 MUST 显式声明其非用户消息、不构成用户对任何操作的授权或同意，且不解除任何确认要求。
- **FR-007**: 自救提醒 MUST 提供三个出口：声明完成并汇报、声明等待用户、从中断处继续。
- **FR-008**: 系统 MUST 区分"输出被长度上限截断"与其他结束原因，并在截断时说明截断后未执行的工具调用。
- **FR-009**: 系统 MUST NOT 对同一轮设置修复次数上限。
- **FR-010**: 系统 MUST 在同一轮达到配置阈值（默认第 5 次）仍未声明时向用户展示"可能卡住"的提示，且该提示在同一轮内只出现一次。
- **FR-011**: 系统 MUST NOT 在用户取消后的本轮发出任何提醒。
- **FR-012**: 系统 MUST NOT 对子助手的轮次设门。
- **FR-013**: 系统 MUST NOT 自行重试失败的模型请求，也不得在请求彻底失败后重启轮次。
- **FR-014**: 系统 MUST NOT 解析助手自然语言判断任务是否完成，完成与否只依据显式声明。
- **FR-015**: 当所需的宿主能力缺失时，系统 MUST 明确报错并自行停用，不得静默失效。
- **FR-016**: 自救提醒的内容 MUST 只由固定文案与受校验的类别构成，不得拼接文件内容或工具输出原文。

### Key Entities

- **目标状态（Target State）**：某一顶层对话轮次内"是否已达成"的判定依据，取值"进行中/已完成/等待用户"；随轮次产生与消失，不跨轮保留。
- **自救提醒（Repair Notice）**：系统在轮次未声明状态时自动投递的一条带来源归属的对话消息，包含原因类别、三个出口与非授权声明。
- **取消标记（Cancellation）**：用户主动中断的信号；出现后本轮不再产生任何提醒。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在被截断或以"未声明"结束的构造用例中，100% 触发一次自救提醒，且提醒中包含当时可判定的原因类别。
- **SC-002**: 声明了"已完成"或"等待用户"的轮次，100% 不被催促（零误伤）。
- **SC-003**: 用户取消后的轮次，触发提醒的次数为 0。
- **SC-004**: 同一轮内连续未声明达到阈值（默认 5）时，100% 出现面向用户的卡住提示；超过阈值后不重复出现。
- **SC-005**: 子助手轮次触发收尾门的次数为 0。
- **SC-006**: 插件在缺少所需宿主能力的环境中启动时，100% 明确报错并停用，不出现"看似启用但从不生效"的状态。
- **SC-007**: 对一次典型的"做一半就收尾"任务，用户无需再次输入即可看到任务被继续推进（人工验收 3 例）。

## Assumptions

- 宿主提供"轮次即将结束但尚未关闭"的拦截点，允许在关闭前追加一步；若无此能力，本特性的核心场景无法实现。
- 宿主提供模型可调用的工具通道，以及带来源归属的对话消息投递通道。
- 宿主能够报告单次生成的结束原因（正常结束 / 长度上限 / 中止 / 错误）。
- 宿主在用户取消时走独立路径，不会进入正常收尾判断。
- 仅覆盖顶层对话；子助手、后台任务、定时任务不在门控范围内。
- 上游请求失败的重试由宿主负责，本特性不重复实现。
- 思考泄露与工具调用畸形属于其他层的职责，本特性不检测、不修复。
