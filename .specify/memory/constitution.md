## 核心原则

### I. 简单性优先

- 能用就行的最简单方案优先；易懂 > 聪明（KISS）
- 公共逻辑只存在一处，禁止复制粘贴编程（DRY）
- 不提前构建不需要的功能，只在必要时增加复杂度（YAGNI）
- 理由：本插件的价值在于"少而准地干预"，一个过度设计的续行器会比任务中断更伤害体验

### II. 测试先行

- **没有失败的测试就不写生产代码**，无例外
- 循环：先写必然失败的测试并实际看到它失败（RED）→ 写刚好够通过的最少代码（GREEN）→ 绿灯后重构，不加新行为（REFACTOR）
- 修 bug 必须先写重现 bug 的失败测试（Prove-It）
- 跑测试用仓库自己的命令（见 AGENTS.md §构建与运行），不臆测 `npm test`
- 理由：本插件的行为是"在异常边界做判断"，这类分支不写测试就无法证明它没有把正常收尾也一并拦下

### III. 提示面与状态安全

本插件直接改写模型可见上下文与轮次边界，因此以下约束按安全红线执行：

- **只能通过日志通道影响模型**：系统提示词章节（`ctx.systemPrompt.section`）、`agent.inject`、`agent.steer`、工具结果。禁止绕过会话日志直接改写历史消息
- **注入必须可审计**：每条自动注入都带来源标记与原因（失败类别、第几次修复），可被会话日志回放
- **注入必须有明确的预算策略**：修复次数上限、阈值触发的用户通知、退避或熔断，至少具备其一并写入规格；禁止既无上限、又无人工介入点的无界重试
- **绝不覆盖用户意图**：用户取消（cancel/abort）不得被自动"复活"；用户明确要求停止后不得再注入
- **禁止无证据的通用催促**：注入必须携带本次失败的具体证据（截断位置、失败类别、未完成的工具调用），不得只发"请继续"
- 理由：一个会自己说话的插件，越权一次就会污染整段对话，且极难归因

### IV. 原子提交与主干开发

- `main` 始终可部署；功能分支短命（1-3 天）；feature flag 优于长分支
- 一次提交做一件逻辑完整的事；提交消息解释 why；格式化/重构与功能变更分开提交
- 实现切片 → 测试 → 验证 → 提交 → 下一切片；禁止堆积后的巨型提交
- 理由：小步快走让回滚、审查、二分定位都保持廉价

### V. 不审查不合并

- 重要功能完成后、合并 main 前必须审查，不因"很简单"跳过
- 审查按五轴：正确性 → 可读性 → 架构 → 安全 → 性能
- 评论必标级别：[必须修复] 阻断合并；[建议修改] 需回应；[仅供参考] 不阻断
- bug fix 必须有回归测试；任何触碰提示词注入、轮次边界、重试策略的变更必须过安全轴
- 理由：本插件的缺陷形态是"悄悄多发一条消息"，不会抛错，只能靠审查与测试发现

### VI. 可读性与显式契约

- 代码被读多于被写：自文档化命名，注释只写 why
- 注释规范遵循 AGENTS.md §注释
- 显式类型签名；禁止 `any` / 非必要断言
- 模块接口先定义契约再实现；一切可观察行为都是承诺（Hyrum's Law）
- 理由：插件跑在别人的 agent loop 里，隐性契约就是"某天 DSH 升级后静默失效"

### VII. 复用宿主机制

DSH 已提供 goal 状态机、goal 续行驱动器、请求级重试、轮次收尾拦截点。本插件：

- **必须先复用**这些机制，只在确有缺口处新增行为
- 新增与宿主重叠的第二套状态（例：另造一套与 `dsh-goal` 平行的目标状态机）必须先写 ADR 并说明缺口
- 与已有续行来源（`dsh-goal-round-driver`）同时挂载时，必须有明确的不重复注入仲裁
- 理由：两套续行逻辑同时生效会互相触发，产生"插件自己跟自己对话"的失控循环

## 宿主集成约束

- 目标版本：DeepSeek-Harness `0.2.1-rc.5`，cordis `~4.0.5`，ESM 插件（导出 `name` / `inject` / `Config` / `apply`）
- 插件形态：独立 npm 包，通过 profile 的 `cordis.patch.yml` `insert` 条目或 `dsh plugin --profile <name> add <pkg>` 挂载
- 依赖 DSH 内部包时使用 `peerDependencies` 并对齐宿主版本；不得把 DSH 私有实现复制进本仓库
- 升级宿主前先跑本仓库的兼容测试，再改版本声明

## 开发工作流

- 规格流程走 `.specify/`（speckit）：`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`
- 设计取舍、事件面调研结论落在 `docs/PLUGIN-DESIGN.md`，实现与文档不一致时以代码为准并回写文档
- 本机为 bash 脚本脚手架：`.specify/scripts/bash/*.sh`（参数用 `--json`），不存在 `*.ps1`

## Governance

- 本宪法优先于其他所有项目惯例；冲突时以宪法为准
- 修订程序：提出修正案 → 说明理由 → 更新版本与 LAST_AMENDED_DATE → 同步检查依赖模板（AGENTS.md、spec/plan/tasks 模板）
- 版本策略（语义化）：MAJOR = 删除或重定义原则；MINOR = 新增原则或实质性扩充；PATCH = 措辞澄清
- 每个实施计划（plan）必须包含宪法合规检查；违反宪法的做法无论多"临时"都不允许
